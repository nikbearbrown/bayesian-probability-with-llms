# Research: Chapter 02 — Prompting for Statistics
## Bayesian Probability with LLMs

**Chapter one-line:** Learn to use an LLM as a statistical implementation partner — describing problems precisely, verifying outputs critically, and iterating toward solutions that match what the math actually requires.

**Research date:** 2026-05-13

## 1. Primary Sources

### Foundational papers and texts

1. **Brown, T. B., Mann, B., Ryder, N., et al. (2020).** "Language Models are Few-Shot Learners." *NeurIPS 2020.* [arXiv:2005.14165](https://arxiv.org/abs/2005.14165). The GPT-3 paper. Establishes the in-context learning paradigm that makes "prompting" a category of skill at all. The relevant claim for this chapter: the model's behavior depends materially on how the request is framed and what examples accompany it. Few-shot is not a fine-tuning trick; it is an interface property the user manipulates by writing differently.

2. **Wei, J., Wang, X., Schuurmans, D., et al. (2022).** "Chain-of-Thought Prompting Elicits Reasoning in Large Language Models." *NeurIPS 2022.* [arXiv:2201.11903](https://arxiv.org/abs/2201.11903). Demonstrates that asking the model to show intermediate steps improves accuracy on multi-step reasoning tasks. Directly motivates Block 2's "ask for the mathematical steps, not just the code" — this is not a stylistic preference, it is documented to change correctness.

3. **Vaithilingam, P., Zhang, T., & Glassman, E. L. (2022).** "Expectation vs. Experience: Evaluating the Usability of Code Generation Tools Powered by Large Language Models." *CHI '22 Extended Abstracts.* [PDF](https://tianyi-zhang.github.io/files/chi2022-lbw-copilot.pdf). 24-participant within-subjects study of GitHub Copilot. The finding the chapter rests on: Copilot did not reduce task completion time or increase success rate, despite users preferring it. Users struggled most with *understanding, editing, and debugging* generated code — exactly the verification skill this chapter teaches.

4. **Liu, J., Xia, C. S., Wang, Y., & Zhang, L. (2023).** "Is Your Code Generated by ChatGPT Really Correct? Rigorous Evaluation of Large Language Models for Code Generation." *NeurIPS 2023.* [arXiv:2305.01210](https://arxiv.org/abs/2305.01210). Introduces EvalPlus / HumanEval+. The empirical headline for the chapter: stricter test suites reduce pass@k by 19.3–28.9% across 26 LLMs. Code that "works" on shallow tests routinely fails on edge cases. This is the quantitative backbone for "plausible-looking wrong answers."

5. **OpenAI (2023).** "GPT-4 Technical Report." [arXiv:2303.08774](https://arxiv.org/abs/2303.08774). Model card / technical report. Cite for the explicit acknowledgment that GPT-4 "still is not fully reliable (it hallucinates facts and makes reasoning errors)" — vendor-acknowledged limitation, useful for legitimizing the verification frame without seeming alarmist.

6. **Liu, F., Liu, Y., Shi, L., et al. (2024).** "Exploring and Evaluating Hallucinations in LLM-Powered Code Generation." Taxonomy of code hallucinations across 5 primary categories; [related ASE paper at arXiv:2404.00971](https://arxiv.org/abs/2404.00971). Useful for naming the failure modes in Block 5 with literature backing rather than anecdote.

7. **Anthropic.** "Prompting best practices." Claude API documentation. [platform.claude.com/docs](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview). Vendor-published prompt engineering reference. Citable for "be specific," "provide examples," "use structured output" — but flag as living documentation, version-stamp when cited.

### Key empirical cases

1. **The HumanEval+ pass rate drop.** Liu et al. (2023) above. GPT-4's pass@1 on HumanEval was reported around 67%; on HumanEval+ it dropped meaningfully. Specific numbers are version-dependent and should be re-checked at draft time.

2. **The Copilot productivity paradox.** Vaithilingam et al. found participants *preferred* Copilot even when it didn't help. This is the chapter's psychological hook: the failure mode is not "students refuse to use the tool" — it is "students trust the tool too much because it feels helpful."

3. **[illustrative]** A student prompts "compute the p-value for a positive medical test" and receives code that computes P(positive | disease) — likelihood — labeled as a p-value. Code runs. Number is plausible. Number is wrong concept. This is the canonical failure mode (Block 5, "Correct code, wrong model") and worth presenting as an explicit worked dialogue rather than an abstract category.

## 2. The Core Concept — State of the Field

### What is settled
- LLMs trained on code can produce syntactically valid output for most well-specified statistical tasks ([Brown et al. 2020](https://arxiv.org/abs/2005.14165); replicated across model families).
- LLMs hallucinate — produce plausible content that is factually or computationally wrong — at non-trivial rates even in 2026's frontier models ([OpenAI 2023](https://arxiv.org/abs/2303.08774); [Liu et al. 2024](https://arxiv.org/abs/2404.00971)).
- Prompt structure measurably affects correctness on reasoning tasks ([Wei et al. 2022](https://arxiv.org/abs/2201.11903)).
- Users systematically over-trust LLM output relative to its actual accuracy ([Vaithilingam et al. 2022](https://tianyi-zhang.github.io/files/chi2022-lbw-copilot.pdf)).

### What is disputed
- Whether prompt engineering is a durable skill or a transient artifact of current model generations. The systematic review by [Velásquez-Henao et al. and others (2025)](https://link.springer.com/article/10.1186/s41239-025-00503-7) on prompt engineering in higher education notes the field has not converged on assessment standards or a stable taxonomy of techniques.
- Whether "chain of thought" is genuine reasoning or pattern-matching that mimics reasoning. The chapter does not need to take a side; it needs to teach the technique while flagging the open question.
- Whether verification by hand calculation scales to problems the student cannot solve by hand. The chapter's position: verification of *structure* (does the model match the problem?) is always available even when verification of *numbers* is not.

### What has changed recently (last 5 years)
- 2020: GPT-3 paper makes few-shot prompting a known interface.
- 2022: Chain-of-thought becomes the dominant prompting pattern for reasoning tasks.
- 2023: ChatGPT (free tier) puts LLM code generation in the hands of undergraduates at scale. EvalPlus (Liu et al.) provides the first rigorous quantification of how much hidden incorrectness benchmarks were missing.
- 2023–2024: Vendor documentation matures (Anthropic, OpenAI publish formal prompt guides). "Tool use" / function calling shifts the interface from chat to agent.
- 2024–2026: Reasoning models (o1, o3, Claude with extended thinking) shift the cost-benefit of chain-of-thought — the model does it internally. This affects what the user needs to ask for explicitly. Major aging risk for any chapter teaching prompting technique.

## 3. Application Domain Examples

This chapter's domain is *prompting for statistics specifically*, not prompting in general. Real documented cases:

1. **Statistical reproducibility in linear regression.** [Hardwicke et al. and related work on computational reproducibility in linear regression](https://www.medrxiv.org/content/10.64898/2026.04.07.26350286v1.full) document that even with original data and code, reproducing published regression results is frequently impossible. The chapter's relevance: an LLM that produces *some* regression output is not producing *the right* regression output unless the user verifies the model spec.

2. **Pandas / NumPy off-by-one and indexing errors.** Documented across the EvalPlus benchmark family ([Liu et al. 2023](https://arxiv.org/abs/2305.01210)). Statistical code is unusually vulnerable to silent indexing bugs because the wrong subset produces a plausible number.

3. **The "Frequentist answer dressed in Bayesian language" failure.** Anecdotal but reported across LLM-assisted statistics courses; flagged by [Greenland et al. (2016)](https://pmc.ncbi.nlm.nih.gov/articles/PMC4877414/) as a misinterpretation pattern that predates LLMs — but LLMs reproduce it because their training data contains the same confusions human authors made.

4. **[illustrative]** Prompting for "the probability the patient has the disease given a positive test" (Chapter 1's problem). A naive prompt frequently elicits code that returns 0.99 (the likelihood) rather than ~0.09 (the posterior). The model is technically computing what was asked for if the prompt was sloppy. The fix is in the prompt, not the model.

5. **Vendor model cards as primary sources.** The [GPT-4 technical report](https://arxiv.org/abs/2303.08774) and [Anthropic's Claude documentation](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview) both acknowledge specific failure modes (reasoning errors, fabricated citations, mathematical mistakes). Teaching students to read these documents is itself part of the skill.

## 4. The Book's Thesis Connection

The book teaches statistical inference by side-by-side frequentist/Bayesian comparison, with LLM-generated code as the implementation layer. That setup is only honest if students can distinguish a correct implementation from a plausible-looking wrong one. Chapter 2 is the load-bearing chapter for that honesty: every later chapter ends with a "Prompting for Implementation" section that assumes the student passed Chapter 2.

The thesis-level claim this chapter makes: **LLMs are an implementation partner, not an oracle.** The student supplies the structure (which framework, what quantity, which assumptions); the LLM supplies the typing. If the student doesn't know enough to specify, the LLM cannot rescue them — and will reliably produce something that looks like a rescue. This is the book's answer to "why teach statistics at all if LLMs can do it" — the LLM cannot do it without a user who can spot when it is doing the wrong thing.

The chapter also previews the book's core epistemic move: specifying the question precisely *before* computing. Frequentist vs. Bayesian is often less a disagreement about answers than a confusion about which question is being asked. A student who learns to write a prompt that names the data generating process, the quantity wanted, and the framework explicitly is doing the same specification work they will do for the rest of the book.

## 5. Intellectual Lineage Notes

Prompting as a named practice is recent (post-2020). The underlying intellectual move — *specify the problem precisely before computing* — is much older.

1. **George Pólya, *How to Solve It* (1945).** [Princeton University Press](https://press.princeton.edu/books/paperback/9780691164076/how-to-solve-it). Pólya's first step is "Understand the problem": *What is the unknown? What are the data? What is the condition?* This is exactly what a good statistical prompt does — it forces the user to name unknown, data, and condition before asking the LLM to compute. The chapter can cite Pólya directly to legitimize the practice as continuous with mathematical pedagogy, not a 2020s novelty.

2. **John Tukey, *Exploratory Data Analysis* (1977).** Addison-Wesley. Tukey's distinction between exploratory and confirmatory analysis maps onto a useful prompting distinction: exploratory prompts ("show me what's in this data") vs. confirmatory prompts ("test this specific hypothesis against this specific model"). The failure mode the chapter warns against is users running confirmatory analyses with exploratory prompts — getting an answer that looks decisive but specified nothing.

3. **Tom Brown et al. (2020).** [arXiv:2005.14165](https://arxiv.org/abs/2005.14165). The proximate ancestor.

4. **Jason Wei et al. (2022).** [arXiv:2201.11903](https://arxiv.org/abs/2201.11903). The proximate ancestor for the "show your work" prompting move.

The deeper claim: prompting is the latest instance of a recurring pedagogical lesson — that articulating a question precisely is most of the work of answering it. Feynman's discipline of explaining a concept until you understand it is the same discipline, run in the opposite direction.

## 6. Pedagogical Delivery Research

The literature on teaching prompting is genuinely thin and largely 2024–2025 vintage.

- **[Velásquez-Henao et al. (2025), "Prompt engineering in higher education: a systematic review."](https://link.springer.com/article/10.1186/s41239-025-00503-7)** Notes the lack of assessment standards and the consensus that prompting is best taught as a critical-thinking exercise with hands-on iteration. Directly supports the chapter's exercise design: the student prompts, then verifies, then iterates.
- **[Vaithilingam et al. (2022)](https://tianyi-zhang.github.io/files/chi2022-lbw-copilot.pdf).** The crucial pedagogical finding: users *like* LLM tools even when they don't help. Teaching strategy implication: comfort with the tool is not evidence of competence with the tool. The chapter has to teach students to distrust their own felt fluency.
- **The "plausible-but-wrong" failure mode.** Surveyed across [Liu et al. (2024)](https://arxiv.org/abs/2404.00971) and the EvalPlus line. The most dangerous LLM outputs are not the obviously broken ones — they're the ones that compile, run, and produce a number in the right ballpark for the wrong reason. The chapter needs at least one worked example where the student must catch this kind of failure.
- **Scaffolded iteration.** The systematic review consensus is that prompt engineering is taught best through guided iteration with feedback — not by lecture. The "shown as a dialogue, not a polished result" instruction in the chapter brief (line 222) is consistent with this evidence.

A specific recommendation: the chapter's worked example should show at least one *iteration loop* — a first prompt, the LLM's output, the student catching an error, the corrected prompt, the corrected output. Polished prompt-and-answer pairs teach the wrong lesson.

The chapter's main display element is the **worked prompting session as dialogue** (TIKTOK.md line 220, 222). What that looks like in the book:

```
USER PROMPT (first attempt):
  "Write Python code to compute the probability someone has 
   a disease given a positive test result, if the test is 
   99% accurate."

LLM OUTPUT (first attempt):
  [code block]
  [explanation that conflates likelihood with posterior]

[ANNOTATION: "Look at the output. The model returned 0.99. 
 But we already know from Chapter 1 that this answer is wrong. 
 What did the prompt fail to specify?"]

USER PROMPT (revised):
  "Compute P(disease | positive test) given disease 
   prevalence P(disease) = 0.001, sensitivity 
   P(positive | disease) = 0.99, and false positive rate 
   P(positive | no disease) = 0.01. Use Bayes' theorem. 
   Show the calculation step by step before writing code."

LLM OUTPUT (revised):
  [code with explicit Bayes' theorem]
  [step-by-step math]
  [result: ~0.09]

[ANNOTATION: "Now the model has the right structure. 
 Verify the answer against the Chapter 1 hand calculation."]
```

Design notes for the author:
- Use a fixed-width font for prompts and outputs; annotations in margin or callout style.
- Show at least one error caught and corrected. Polished examples mislead.
- Pair every prompt example with a one-line statement of what the prompt *specifies* (DGP, quantity, framework) and what it leaves implicit.
- Date-stamp model names ("GPT-4o, output retrieved 2026-XX-XX"). Outputs will not reproduce identically across versions.

## 8. Open Questions and Research Gaps

### Aging risk — this chapter has more than any other in the book
Specific aging risks to flag in the draft:
1. **Model names and versions.** Any reference to "GPT-4," "Claude 3.5 Sonnet," or a specific Gemini version will be outdated within 12–24 months. The chapter should refer to "the LLM you have access to" in body text and confine version-stamps to figure captions.
2. **Specific prompt patterns.** "Chain-of-thought" was an effective technique when [Wei et al. (2022)](https://arxiv.org/abs/2201.11903) was published. By 2026, reasoning models do it internally; explicitly prompting for it can be redundant or even counterproductive. The chapter should teach the *underlying move* (ask for steps, not just answers) and note that specific syntactic patterns will date.
3. **Failure mode prevalence.** The specific frequency of hallucinations and code bugs cited (e.g., 19–29% pass@k reduction from EvalPlus) is a 2023 number on 2023 models. The chapter should cite it and note that the *pattern* persists even as the numbers improve.
4. **Tool integration.** As of 2026, LLMs can execute code, retrieve documents, and run statistical packages directly. By the next edition, the "prompt → user copies code → user runs code" workflow may itself be obsolete.

### Research gaps where the chapter must take a position without strong empirical backing
- **How much verification is enough?** No empirical literature settles whether the student should re-derive every result by hand, only spot-check, or rely on cross-model verification. The chapter should be explicit that it is teaching a *floor* (verify the structure, spot-check the numbers), not a *ceiling*.
- **Whether LLM-assisted prompting *teaches* statistics or substitutes for learning it.** This is the elephant in the chapter. The book's whole thesis assumes the answer is "teaches, if done right." That assumption is not yet empirically settled.

### Mechanism gaps
- Why some prompt patterns work is poorly understood even by model developers. The chapter should treat prompt engineering as engineering — empirically grounded craft — not as a science with worked-out causal laws.

- **No paywalled primary sources** are required for this chapter — every key citation has a public preprint or open-access version.
